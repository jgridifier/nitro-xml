# 0.1.0 — E1 editing release candidate

Status: candidate, pending Head of Product PASS and manual npm publication.
Packages: `nitro-xml@0.1.0` and `@nitro-xml/react@0.1.0`.

View and edit DOCX, XLSX and PPTX in a browser with the Rust/WASM engine and
React `NitroViewer`. React 18+ and React DOM 18+ are peers; the binding depends on
`nitro-xml ^0.1.0`. The host owns persistence: `ref.current.save()` returns
`Promise<Uint8Array>`; upload or download those bytes in your application.
`onChange` reports saved bytes, not every keystroke. The library does not upload
files. `editable` defaults to false. Give the component a nonzero height and
supply `fileName` when passing raw bytes. Import is SSR-safe; interactive hosts
in frameworks using server components need a client component boundary.

## Install and embed

After publication:

```sh
npm install nitro-xml@0.1.0 @nitro-xml/react@0.1.0 react react-dom
```
```tsx
import { useRef, useState } from "react";
import { NitroViewer, type NitroViewerHandle } from "@nitro-xml/react";

export function Editor({ file, fileName, persist }: {
  file: File | Uint8Array;
  fileName: string; // e.g. report.docx, budget.xlsx or slides.pptx
  persist: (bytes: Uint8Array) => Promise<void>;
}) {
  const ref = useRef<NitroViewerHandle>(null);
  const [ready, setReady] = useState(false);
  const [error, setError] = useState("");
  async function save() {
    try {
      if (ref.current) await persist(await ref.current.save());
    } catch (e) { setError(String(e)); }
  }
  return <>
    <button disabled={!ready} onClick={save}>Save</button>
    <p role="alert">{error}</p>
    <NitroViewer key={fileName} ref={ref} file={file} fileName={fileName}
      editable mode="embedded" style={{ height: 600 }}
      onReady={() => setReady(true)} onError={e => setError(e.message)} />
  </>;
}
```

For Vite production builds, keep dynamically imported worker chunks as ES modules:

```js
// vite.config.js
import { defineConfig } from "vite";
export default defineConfig({ worker: { format: "es" } });
```


Mount a new editor when replacing the document; disable host save while it loads.
`onError` exposes open/paint/save errors; imperative saves also reject.
See [packed consumer example](../../examples/consumer-smoke/) for the actual
Vite production build/install/open/edit/save check.

## Edit scope and evidence

The executable inventory is [`edits/*/*.json`](../../edits/), not a promise of
complete Office authoring support. Commands use `command` in `applyEdit()`;
corpus JSON uses `op`, and some oracle operations have different editor commands
(for example `reorderSlide` maps to `insert.move-slide-to`). The [November 10 audit](../ux-interaction-audit-2026-11-10.md)
separates Rust parity, model-only commands and saved-package validation.

| Format | Edit families represented in the corpus |
|---|---|
| XLSX | Cell text, numbers, booleans, formulas; batches; font/fill/alignment/number formatting; inserted/deleted rows and columns with formula references; add/rename/delete sheets; undo/redo |
| DOCX | Paragraph text/alignment, run bold/italic/underline/size/color; table cell text and inserted/deleted rows/columns |
| PPTX | Shape text/style/fill/line/geometry (move, resize, rotate), add/delete/duplicate/group/ungroup and z-order; slide add/delete/duplicate/reorder; notes, paragraph/run/bullet/autofit and table edits |

DOCX revision acceptance/rejection and comment add/reply/resolve scripts are
**model-only** in the audit: do not treat them as validated persisted features.
The audit skips Rust parity for 15 PPTX slide/table/text suboperations; their TS
oracle validation does not prove Rust save parity. This release's packed
consumer additionally exercises Rust slide reorder; it does not close all those
coverage gaps. XLSX formula edits mark dependents stale and request recalculation
on Office open; this release is not a complete Excel calculation engine.

Known interaction limitations remain: DOCX selection/copy/cut; XLSX IME,
header selection, column resize and fill-mode choice; touch gesture handling.
The audit found no E1 content-loss/blank-page/save-corruption blocker, but these
UX failures remain visible and are not waived by package smoke tests.

## Limits and recovery

- Compressed input: 50 MiB; at most 10,000 parts; 300 MiB total uncompressed;
  200 MiB per part. The viewer additionally caps `word/document.xml` at 25 MiB.
  Compression-ratio protection rejects ratios over 1,000 for sufficiently large
  parts. Oversize packages fail with typed errors and “Package too large.”
- Macro-enabled and template variants open without executing macros. VBA and
  unknown package parts are preserved as opaque bytes. Legacy binary Office,
  encrypted/password-protected documents and other formats are unsupported.
- WASM is required; no TypeScript engine fallback. A viewer crash reloads once
  in a fresh worker. Editor recovery replays the operation journal and undo
  state; failed recovery shows an error/last-save guidance. Recovery is not
  durable host storage: the application must save the returned bytes.
- Fonts, available browser memory and browser capabilities affect rendering.
  These package limits are not a guarantee that every device can edit a file
  of that size. Worker request timeout is 120 seconds.

## Performance losses — retained, not waived

See [M1 report §5.5](../M1-REPORT.md#55-pr-502-ci-perf-tables--8a0ffbe--37c5336)
for measured CI evidence on `37c5336` (Node cold-open S/M/L, not browser first paint):

| Peak memory | WASM / TS | Status |
|---|---:|---|
| DOCX L | **1.151×**, 95% CI [1.131, 1.162]; 210.4 vs 182.8 MiB | **Unattributed regression**, previously 0.932×; not covered by an accepted exception |
| XLSX S | **2.710×** | Accepted first-open compile-floor loss |
| DOCX S | **4.870×** | Accepted first-open compile-floor loss |
| DOCX M | **2.272×** | Accepted first-open compile-floor loss |

The same run reports cold open time wins on all nine S/M/L format cells.
Report-mode CI green does **not** mean all performance gates beat TS. No
thresholds or budgets are changed for this candidate. Full performance runs
were intentionally not repeated on the shared low-memory release-prep box.

## Release review

`bash scripts/ci/consumer_smoke.sh` checks both dry-run file lists, installs the
packed tarballs into a temporary app, builds Vite and validates three real saved
files using Open XML SDK and LibreOffice. `NITRO_HANDCHECK=1` selects ten Office
review cases; the output directory contains matching originals, exact commands,
validation results and a short review checklist. Human Office review and Head
of Product PASS remain required before publication. Nothing here publishes npm
packages or changes the outstanding M1 gate status in the report.
